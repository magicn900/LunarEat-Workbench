# Publishing and implementation alignment

To withdraw a publication, first inspect its id, revision and withdrawalBlocker through versions list/inspect. A null blocker means eligible at inspection time; the server rechecks on execution. With explicit user intent, call versions {action:"withdraw",id,revision} with --task ID (the client supplies requestId). Requires workspace.write and design.publish and the publisher's own account. Only the latest publication can be withdrawn, with no dependent workspaces/versions, no implementation confirmation history (including revoked confirmations), and no subsequent draft changes. This restores the previous formal version, removes the publication record without a withdrawal audit entry, and keeps content, title and description in the publisher's draft. versions review returns publicationDraft with the preserved title/description for republishing. Release control afterward. Withdrawal is not history undo or draft discard. Never withdraw someone else's publication or bypass a blocker.

Use agent (node scripts/agent.mjs) with --profile NAME. These operations require separate permissions and explicit user intent. Discover per-action schemas with help versions.ACTION.

versions {action:"review"} returns bounded draft-vs-base differences, fixed base/draft/main source references and a review handle. Follow all necessary pages before publishing. Conflicts/diagnostics may be partial; incomplete review is not permission to publish. versions {action:"publish",review,title,description} with --task ID publishes the reviewed draft directly, without a separate approval process. Both draft and main must still match. Release afterward.

To discard, versions {action:"discard-preview",review,targets:[{id,key?}]} expands actual affected targets/dependencies. Omit key for the whole file. Inspect impact and issues, confirm unintended dependencies with the user, then versions {action:"discard",plan} with --task ID. Discard changes drafts and restores their baseline, not latest main. It is undoable. Do not treat discard as merely deselecting a publication.

## Merge published updates into a personal draft

Read help versions.refresh once if its contract is not already available, then obtain versions {action:"review"}. incoming and conflictDetails each contain {count,receipt}, frozen to this review. Use read {receipt:RECEIPT}: incoming summaries establish affected scope; follow all conflictDetails pages because every conflict must be resolved. The first ten conflicts in review metadata are only a summary. No conflicts means you can refresh after checking scope, without rereading automatically merged bodies.

An incomplete incoming field is not a request to read its full before/after values. Expand only conflicts, dependencies needed for a design decision, or content the user explicitly asks to review; use sources.base/main for those fixed values. Each conflict has an exact path and base/ours/theirs sides with exists/complete flags. Small values are inline; for a decision requiring missing content, follow the side's read/next. If valuePath is nonempty, decode the returned entity and extract that path. Missing values differ from empty strings. Small body conflicts include segments (automatic text or conflicting line arrays); otherwise segmentsComplete is false. Use supplied complete segments where sufficient. A custom body must preserve all non-conflicting content: read the remaining relevant body ranges if needed to assemble it. Never decide a conflict from truncated samples or treat an incomplete list as exhaustive.

After analysis, create new-task and call versions {action:"refresh",review,resolutions} with --task ID. resolutions maps every exact conflict path to "ours", "theirs", or {"value":CUSTOM_JSON_VALUE}. Custom body values must be the complete merged body, including non-conflicting content, not just a conflict block. Use a string for text, proper JSON types for structured fields, and an explicit deleted side to remove content. Ask the user about ambiguous design intent; never choose all sides just to bypass a conflict. This updates only the personal draft and its baseline, not the published version. Draft/main changes invalidate the review: obtain a new review and reconcile again instead of copying stale choices. The client manages request IDs and write sessions; retry an uncertain request unchanged and release --task ID when finished.

versions {action:"list"} returns publication summaries and sync status. Inspect {action:"inspect",id} for differences at fixed revisions. Use read/find/query with revision or returned snapshot references for precise formal design context; do not compare implementation against a moving draft.

A programmer/coding agent must inspect actual code and the relevant fixed design revision before versions {action:"sync",ids:[PUBLICATION_ID],repository,commit,note,active:true} with --task ID. Record a real commit and verification evidence. A code change may be unnecessary, but code inspection is not optional. active:false returns the record to pending while preserving history. This API records a confirmation, not proof that code is correct. Never mark unverified examples synchronized.
